Ten lessons from Tracktion Engine

A synthesis after building the twelve diagrams. These are the moves that reshaped my mental model of what a DAW is — ordered roughly from "spine of the architecture" out to "how the realtime contract is kept." If you only read the diagrams for one thing, read them for these.

  1. The Edit is a juce::ValueTree, not a custom object graph.

    Tracks, clips, plugins, automation, tempos — almost everything in the document is reflected through ValueTree nodes. Undo, dirty-tracking, change notification, and serialization all come from one mechanism. The classes you read in tracktion_Track.h are typed views over a generic observable document. This is the move I'd steal first.

    diagram 03 — the Edit

  2. The live audio graph IS the offline render graph.

    createNodeForEdit(Edit&) returns the same DAG that the realtime player and the offline renderer both consume. Freeze, nested-edit baking, warp, stems, user export — each is an EditRenderJob specialization driving the same node tree. "Render doesn't match playback" is closed by construction, not by tests.

    diagram 04 — rendering graph · diagram 12 — rendering

  3. Routing is a plugin.

    VolumeAndPan, AuxSend, AuxReturn, InsertSend, RackInstance, FreezePoint — all Plugin subclasses living in the plugin chain. There is no separate mixer/router primitive. The chain ordering you see in the UI is the signal flow.

    diagram 06 — plugin system

  4. Racks are shared sub-graphs.

    A RackType defines a small graph; RackInstances place it in larger graphs and share the DSP. That's how you get a modular-synth pattern inside a linear-timeline DAW without paying for it N times.

    diagram 06 — plugin system

  5. Recording is always-on; transport just commits it.

    Every armed input continuously fills a retrospectiveBuffer (default 30 seconds). Hitting record doesn't open a writer — it slices what's already been captured. "What was that thing I just played?" is the default, not a feature.

    diagram 10 — recording & comping

  6. The MIDI output dispatcher is deliberately off the audio thread.

    MidiNoteDispatcher is a juce::HighResolutionTimer, not a callback consumer. If you bound MIDI-out timing to audio block boundaries, your latency floor would be the block size. Audio and MIDI are on related but separate clocks for a reason.

    diagram 05 — transport · diagram 07 — MIDI

  7. There's no homegrown realtime toolkit.

    Tracktion composes seven vendored libraries — farbot, moodycamel/concurrentqueue, crill, rigtorp/SPSCQueue, rpmalloc, choc, libsamplerate — each solving one narrow lock-free or realtime problem. The lesson is restraint: don't write your own SPSC queue, your own seqlock, your own RT allocator. Pick the best one and stop.

    diagram 02 — module graph · diagram 09 — threading

  8. Plugin construction is a std::function factory.

    createPluginInstance is a registered callable per type. That single indirection is what lets internal plugins, VST/AU/CLAP wrappers, ARA hosts, and Racks all live in one chain without the host caring which kind it has.

    diagram 06 — plugin system

  9. Automation is recursive because the type system is.

    A Modifier (LFO / envelope / random / breakpoint / MIDI-tracker) is itself an AutomatableEditItem. A MacroParameter is itself an AutomatableParameter. So you can automate the macro that drives a parameter that's also being driven by an LFO, and nothing about the model has to special-case it.

    diagram 11 — automation

  10. The audio thread is a contract, not a function.

    It cannot wait, allocate, or lock. Everything else — MultipleWriterSeqLock, lock-free FIFOs, async value-tree updates, ScopedSteadyLoad, the worker pool's six selectable strategies — exists to let the rest of the system mutate state without making the audio thread block. Once you read it that way, the thread diagram stops looking complicated and starts looking inevitable.

    diagram 09 — threading

Two honourable mentions that didn't make the cut. CompManager is SingleThreadedReferenceCountedObject — comping is explicitly a UI-thread concern, and the audio graph only ever sees the flattened result. And TimeStretcher is a compile-time façade over Elastique / RubberBand / SoundTouch / ARA — build-time choice, not runtime polymorphism, traded off against a small loss of flexibility for cleaner code paths and simpler licensing.

Built against Tracktion Engine 3.2.0, commit 2877b621. For the long-form versions, walk the twelve diagrams.
