04 · the audio DAG

The rendering graph

How an Edit becomes a tree of Node objects that a real-time player walks every audio block. One side generic (tracktion_graph), the other engine-specific (tracktion_engine/playback/graph/), with a single bridge function — createNodeForEdit — in between.

Concept: two halves joined at one function

A playing Edit is a DAG. Every audio block, a player calls process() on a root Node, which recursively pulls samples from its children until the leaves — audio-file readers, MIDI sequences, live device inputs — produce the data. The player is in tracktion_graph. So is the Node base class. So is PlayHead. None of them know anything about Edits, Tracks, or Clips. The DAW-specific node types — a node that knows how to read a wave file at a given speed, one that hosts a plugin, one that represents a rack — all live next door in tracktion_engine/playback/graph/.

The two halves meet at a single free function: createNodeForEdit. Two overloads exist, one taking an EditPlaybackContext for live playback and one taking just an Edit& for offline rendering. Both walk the Edit, build a tree of engine-specific Nodes, and return a std::unique_ptr<tracktion::graph::Node> — the opaque root the player holds.

Implementation: builder, player, and a catalogue of Node types

The builder lives in tracktion_EditNodeBuilder.cpp. Its inputs are explicit and worth reading: a ProcessState shared across the whole graph, a sample rate, a block size, optional allowedClips / allowedTracks masks, and flags like forRendering (skip freeze files), includePlugins, includeBypassedPlugins, and allowClipSlots. Those knobs let the same builder produce very different trees: a minimal tree for rendering one clip in isolation, or the full live-playback tree with metering, comping, fades, aux sends, and device I/O.

The player is LockFreeMultiThreadedNodePlayer — the production path — backed by NodePlayerThreadPools. A simpler NodePlayer exists for tests and reference. Both walk the same Node tree; the multi-threaded one schedules independent sub-trees across workers without locks. Node types on the engine side fall into families: sources (WaveNode, MidiNode, TimeStretchingWaveNode, ClickNode); transforms (PluginNode, ModifierNode, FadeInOutNode, CombiningNode, ContainerClipNode); routing (RackNode, RackInstanceNode, RackReturnNode, AuxSendNode, InsertSendNode); and I/O (WaveInputDeviceNode, MidiInputDeviceNode, LiveMidiOutputNode, MidiOutputDeviceInstanceInjectingNode).

Tradeoff: a generic DAG with a DAW-sized catalogue pasted on

The upside of the split is that the graph module stays reusable — a project that wants a realtime DAG processor without a DAW can link just tracktion_graph and write its own Node types. The downside is the sheer length of the engine-side catalogue. There are roughly thirty Node subclasses in playback/graph/, most of them small, each responsible for one feature (looping MIDI, arranger-launcher switching, dynamic time offsets for nested Edits, level metering, insert round-trips). The catalogue reads like a changelog — every time the DAW grew, a new Node landed. Useful, but browsing it takes real effort.
