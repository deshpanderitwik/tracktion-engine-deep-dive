07 · MIDI

The MIDI pipeline

MIDI follows the same shape as audio but with its own data types. MidiList is the document-side store; MidiNode streams it into the graph; live input comes from MidiInputDevice and out through MidiNoteDispatcher on its own thread. Musicality — chords, scales, patterns — sits on top as the higher-level layer.

Concept: document, streamer, dispatcher

MIDI in Tracktion Engine has three layers with sharp edges between them. At the top, the document layer — MidiList, MidiNote, MidiControllerEvent, MidiSysexEvent, MidiExpression — lives in tracktion_engine/midi/. It's pure data, backed by ValueTree rows, edited by the UI, serialised to the Edit.

In the middle, the streamer. A MidiClip on a track owns a MidiList. At render time createNodeForEdit turns each MidiClip into a MidiNode — a Node subclass that pulls events out of the list, loops, offsets, and emits them into the graph as timestamped messages. ActiveNoteList tracks the note-on/note-off balance so the node can issue correct note-offs across loop boundaries and stops.

At the bottom, the dispatcher. Outbound MIDI leaves the graph via MidiOutputDeviceInstanceInjectingNode and LiveMidiOutputNode, gets queued, and is sent to hardware by MidiNoteDispatcher on its own juce::HighResolutionTimer thread (flagged in diagram 5). Inbound MIDI from MidiInputDevice enters the graph through MidiInputDeviceNode.

Implementation: each layer has its own event type

The document layer has typed events, not raw juce::MidiMessages. MidiNote carries start beat, length, pitch, velocity, mute flag, and colour; MidiControllerEvent is (beat, controller number, value); MidiSysexEvent carries a byte vector; MidiExpression captures MPE per-note expression (slide, pressure, glide). MidiList also tracks channel and musical context (key, scale) so the editor can reason about chords and scale-degrees.

The graph-side MidiNode is a tracktion::graph::Node final that sits alongside WaveNode from diagram 4. It needs a quantise mode, a live-input flag, and the MidiList to walk. Per block it figures out the block's time range in beats, asks the list for events in that range, translates them to sample offsets within the block, and emits them. MidiNodeHelpers is the shared helper code that MidiNode, MidiInputDeviceNode, and the combining node all use — time-range to event-range conversion, active-note accounting, MPE trim at clip boundaries.

MidiPatchBay and MidiModifier live in plugins/effects/ and are Plugin subclasses that transform MIDI inline: patch-bay routes channels, modifier transposes / velocity-scales / filters. They appear in the track plugin list like any other effect (diagram 6, flag 1).

Above the raw event layer sits Musicality (tracktion_Musicality.h): Chord, Scale, PatternGenerator, KeyResult. These let the engine and UI reason about MIDI musically — what key a clip is in, what chord a selection implies, what notes a generated pattern should produce. MidiProgramManager handles program-change metadata (soundfont-style program naming).

Tradeoff: typed events vs. flat MidiMessage

Using typed event classes (MidiNote, MidiControllerEvent) instead of flat juce::MidiMessages in the document costs some translation at the boundary — MidiNode has to convert typed events back into juce::MidiMessage for hosting plugins and devices. The upside is that editing, undo, MPE semantics, and the UI all get structured data: selecting a note in the piano roll is selecting a MidiNote, not parsing a triplet of MidiMessages. Given how much editor work relies on that structure, the translation cost is clearly worth it.

The dispatcher split (MIDI-out on a timer thread, not the audio thread) was covered as a flag in diagram 5; it deserves to be re-emphasised here because it's the single most important structural decision in this subsystem.

Open questions
