Rendering & export

Offline rendering is the same graph from diagram 4, driven faster than realtime by a Renderer into a file. Freeze, warp-time, reverse clips, edit-within-edit nesting, and bounce-to-track all go through the same RenderManager job queue. One pipeline, many consumers.

Concept: the offline cousin of the live graph

Offline rendering in Tracktion Engine is not a separate system. It uses the same Node graph from diagram 4, the same createNodeForEdit builder, the same Plugin::applyToBuffer calls. The only change is that a NodeRenderContext drives the graph block-by-block at whatever speed the CPU can sustain, writing samples to a file instead of a device. The second overload of createNodeForEdit — the one that takes Edit& instead of EditPlaybackContext& — exists specifically for this.

Renderer is the public entry point. It takes a RenderOptions describing format, bit depth, time range, stems, dithering. EditRenderer specialises it for full-Edit renders. An ExportJob wraps any render as a juce::ThreadPoolJob with progress reporting so the UI can show a bar. RenderManager (a DeletedAtShutdown singleton) owns the thread pool and coordinates jobs — no two renders of the same output file can run at once.

Implementation: four families of render job

Full-Edit renders — the user clicks "Export" — go through EditRenderer + RenderOptions. Options include selected tracks (for stems), time range, normalise, sample rate, format (WAV/FLAC/MP3/etc, delegating to diagram 8's format stack), dithering.

Freeze (diagram 10) uses EditClipRenderJob indirectly: the freeze file for a track is rendered via the same machinery, but with only that track's chain selected. On completion the graph builder picks up the file next time playback starts.

Clip-level baked effects — warp-time and reverse — are rendered into new audio files that replace the clip's source. WarpTimeRenderJob bakes time-stretch edits and ReverseRenderJob produces reversed audio. Both exist because doing these live every block would be expensive and deterministic-enough-to-bake.

Nested edits — a clip that contains another Edit — use EditClipRenderJob to render the sub-Edit to a file that the parent then plays. This is how hierarchical composition works without making every block a recursive render. EditRenderJob is the generic job type both sub-edit rendering and freeze sit on top of.

Glue: Exportable is the interface any renderable object implements. It answers "what are your source files" and "what destinations" so the exporter can gather dependencies, check for missing files, and package multiple stems at once. DAWprojectExport is a separate path — it's the open project-interchange format (Bitwig's .dawproject), which doesn't render audio but exports the Edit's structure.

Tradeoff: one graph for live and offline

Reusing the live graph for offline render is a correctness win — what you hear is what you get, byte-for-byte — but it does mean the graph has to be tolerant of being driven faster than realtime. Most parts are: Node::process takes time in sample frames, not wall-clock time, so it doesn't care how fast blocks arrive. The places that do care — live MIDI inputs, live audio inputs, plugins that depend on wall-clock timing — are skipped by the offline overload of createNodeForEdit (there's no MidiInputDeviceNode in an offline graph).

The job-queue design pays dividends: a DAW with 50 tracks freezing in parallel, or an export of 20 stems, or a nested Edit whose children also need rendering, all go through RenderManager's queue with proper dependency handling. The cost is that the render path has several entry points (Renderer, EditRenderer, EditClipRenderJob, WarpTimeRenderJob, ReverseRenderJob) that all look alike but have subtle differences in what part of the Edit they include.

Open questions

Does the renderer re-use the production LockFreeMultiThreadedNodePlayer, or fall back to the simpler NodePlayer for determinism? Offline rendering usually wants reproducible output, which argues for the single-threaded reference player. Worth confirming against Renderer.cpp before the glossary.

Notable omission: the MP3 / AAC encoder plumbing is in diagram 8 (format stack), not here. The renderer uses the format layer as-is — it doesn't know anything about MP3.
