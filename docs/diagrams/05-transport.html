Transport & playback

The chain that runs when the user hits the spacebar. TransportControl is the public facade, EditPlaybackContext is the per-Edit runtime, and PlayHead — living one module over, in tracktion_graph — is the actual clock. Devices, MIDI dispatch, and external sync hang off the sides.

Concept: a facade, a runtime, and a clock

Every DAW has a transport: play, stop, record, seek, loop. In Tracktion Engine those verbs live on a single class — TransportControl — that sits on the Edit and offers a minimal public surface (play(), record(), stop(), setPosition(), setLoopRange()). The surface is narrow on purpose. Behind it a larger runtime object, EditPlaybackContext, holds the per-Edit state a playing session actually needs: the tree of device instances, the built graph root, a SyncPoint that relates timeline time to reference samples. TransportControl delegates to it for anything that isn't just a flag flip.

The actual clock is tracktion::graph::PlayHead. It lives in tracktion_graph, not in tracktion_engine. That is deliberate — the graph module already carries the concept of transport-relative time, and pulling it up into the engine would force the generic DAG processor to depend on DAW types. TransportControl never touches PlayHead directly; it asks EditPlaybackContext, which then drives the PlayHead that every Node::process() call reads from.

Implementation: who calls whom on press-play

TransportControl::play() calls ensureContextAllocated(), which lazily builds an EditPlaybackContext if one does not exist. EditPlaybackContext in turn asks DeviceManager — owned by the Engine — for the current audio and MIDI device handles, spins up WaveInputDeviceInstance and MidiInputDeviceInstance objects for each, calls createPlayAudioNodes() to invoke createNodeForEdit from diagram 4, and hands the resulting Node tree to a LockFreeMultiThreadedNodePlayer. Finally it calls PlayHead::play(range, looped) and the audio callback starts pulling blocks.

MIDI output is its own thread. MidiNoteDispatcher is declared class MidiNoteDispatcher : private juce::HighResolutionTimer — the audio thread writes timestamped events into a queue and a separate high-res timer callback (hiResTimerCallback()) actually drives the hardware. That split is not incidental; sending MIDI out of the audio callback jitters under load, and a dedicated timer lets the audio block finish without being gated on device writes.

AbletonLink is the interesting external-sync path. It is constructed with a TransportControl&, and its Link callbacks call TransportControl::requestStartStopChange() and requestTempoChange() — flowing into the transport from outside. ExternalPlayheadSynchroniser is the mirror image: it adapts an Edit so a hosting AudioProcessor can drive its transport (call synchronise() in processBlock). The two bracket the transport from both sides.

Tradeoff: one runtime object, many hands on it

EditPlaybackContext has a lot going on. It carries device-instance lists, the built graph, a SyncPoint, pending position changes posted from the UI thread via postPosition(), a speed-compensation factor, tempo adjustment from Link, per-device recording state, and a ScopedDeviceListReleaser for safe reconfiguration. That breadth is the cost of keeping TransportControl's public surface small: every responsibility that isn't "toggle a bool" ends up here. The alternative — a family of smaller runtime objects — would shift the complexity onto callers who'd have to orchestrate them, so the concentration is a reasonable choice. It does mean reading EditPlaybackContext.h takes longer than reading the transport header.

Open questions
