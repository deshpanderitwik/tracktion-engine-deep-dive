Threading & realtime safety

The engine runs on half a dozen threads and trusts none of them to hold a lock for long. A scheduler splits the Node graph across workers; a toolkit of single-producer queues, hazard pointers, and realtime-safe allocators keeps the audio callback from touching anything that blocks.

Concept: many threads, one inviolable one

A playing DAW has at least these threads active: the audio callback (provided by the OS / host), the message thread (UI, ValueTree dispatch), disk workers (reading audio files, generating proxies, writing recordings), the MIDI high-res timer (for outbound MIDI), the plugin-scan process, and — during playback — a pool of audio-graph workers. The rule is simple and absolute: the audio thread must not lock, allocate, or call anything that might block. Everything else exists to keep that rule true.

LockFreeMultiThreadedNodePlayer is the scheduler for the graph. Each audio block, it walks the Node DAG and dispatches independent sub-trees to worker threads. Workers pull from a queue, process, and signal when done; the callback thread assembles the root output. No mutex is taken on the critical path. Workers are created by a ThreadPoolCreator — a function picked from six pooling strategies (conditionVariable, realTime, hybrid, semaphore, lightweightSemaphore, lightweightSemHybrid) so embedders can pick the tradeoff between idle-CPU and wake-up latency that fits their platform.

Implementation: the realtime-safety toolkit

Third-party libraries doing the heavy lifting: farbot (fifo, wait-free primitives by hogliux) is vendored inside tracktion_graph/3rd_party/farbot/. moodycamel::concurrentqueue provides the MPMC queue used for inter-thread messages. moodycamel::lightweightsemaphore is the spin/sleep hybrid the lightweight pool strategies use. crill contributes realtime primitives (spin locks, progressive backoff helpers). rigtorp::SPSCQueue is used where single-producer single-consumer is enough. rpmalloc is a realtime-friendly allocator option. choc supplies lock-free buffers and string utilities.

On top of those, the engine contributes its own pieces: tracktion_core::threads::MultipleWriterSeqLock is a sequence-lock for situations where a few writers update infrequently but many readers poll (Link tempo updates, UI- driven parameter writes). ScopedSteadyLoad is a RAII helper that bounds the audio thread's work-per-block under stress.

The boundaries between threads use specific patterns: UI → audio goes through ValueTree change listeners that set a flag on the message thread, which the audio thread reads atomically next block. UI → audio for position changes goes through EditPlaybackContext::postPosition(), whose pending state the audio thread consumes at the start of the next block. Audio → UI goes through message queues and async updaters. Audio → disk goes through the AudioFifo ring buffers and the AudioFileCache read-ahead path. Audio → MIDI out goes through MidiNoteDispatcher's high-res-timer thread.

Tradeoff: lock-free is not free

Lock-free code is harder to write, harder to audit, and harder to port than locked code. The engine pays that cost because the alternative — a priority-inverted audio thread waiting on the UI thread once per block — is not a tradeoff: it's a guarantee of glitches. The six-strategy ThreadPoolCreator reflects the other side of the cost: no single worker-idle strategy is right for all platforms. Servers want condition variables (let idle cores sleep). Low-latency mobile wants spin-with-progressive- backoff (wake up instantly). The engine refuses to pick, so embedders pick.

The engine also tolerates dependency weight here in a way it doesn't elsewhere. Seven third-party libraries to keep the audio thread quiet is a lot of surface. The alternative — rolling in-house SPSC queues, semaphores, allocators — is a deep rabbit hole and has burned other DAWs before. Using published, audited libraries is the right call.

Open questions
