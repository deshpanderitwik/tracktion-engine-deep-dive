Recording, comping & freeze

Three related paths that all commit audio to disk: recording captures an input, comping stitches the best bits of multiple takes, and freeze bakes a track's live graph into a wave file to save CPU. They share the same plumbing — an InputDeviceInstance, a retrospective buffer, and a background writer thread.

Concept: capture, stitch, bake

Recording is the act of writing an incoming signal to disk and then inserting a clip that references the file. In Tracktion Engine the live side of that lives on InputDeviceInstance and its per-device RecordingContext, hanging off the EditPlaybackContext from diagram 5. Wave input goes through a dedicated WaveInputRecordingThread (a juce::Thread) that drains an audio FIFO and writes the file; MIDI input uses a MidiRecordingContext that accumulates events into a MidiList directly.

Comping is an editor-side concept: a track can have multiple takes (each a sibling clip on the same source), and the user picks sections from each to form the final comped playback. CompManager and its subclasses (WaveCompManager, MidiCompManager) own that relationship. TrackCompManager collects track-level comp metadata.

Freeze is the DAW feature where you commit a track's live processing to a rendered audio file so the engine can play the file instead of the full plugin chain. The engine's FreezePointPlugin (an internal Plugin from diagram 6) marks the point in the chain where freezing cuts; the actual render reuses diagram 12's rendering machinery. At playback, if a freeze file exists the graph builder (createNodeForEdit) skips the upstream plugins and plays the wave instead.

Implementation: shared plumbing, different destinations

The entry point is on TransportControl: record() plus stopRecording(). The state lives on EditPlaybackContext (prepareForRecording, numActivelyRecordingDevices, and the applyRetrospectiveRecord() that consumes the retrospective buffer). Each InputDeviceInstance owns a RecordingContext that tracks start time, punch in/out, and the file currently being written.

Retrospective record is a nice touch. Even when not recording, each input device maintains a ring buffer of the last N seconds of incoming audio / MIDI (default 30 s, via SettingID::retrospectiveRecord). Hit "oh, I should have been recording" and applyRetrospectiveRecord() creates clips from the buffer contents. The retrospective buffer lives on InputDevice; a retrospectiveRecordLock flag lets the UI guarantee the buffer can't be clobbered while the user is deciding.

Comp managers are single-threaded ref-counted (juce::SingleThreadedReferenceCountedObject) and editor-thread-only. They do not touch the audio thread — the playback side sees comped material as regular clips in a CombiningNode, the same path a normal multi-clip track uses.

Freeze uses the render machinery from diagram 12 but stores the result alongside the Edit (and tags it so the graph builder can find it). FreezePointPlugin is where the chain is cut; when frozen, the createNodeForEdit builder emits a WaveNode pointing at the freeze file and skips everything upstream of the freeze-point plugin.

Tradeoff: one retrospective buffer, many takes

Retrospective record is a single ring per input. If the user wants to retrospectively capture a take they played 90 s ago and the buffer is 30 s, it's gone. Making the buffer bigger costs memory linear in every-input-times-seconds, and default 30 s per input already adds up on a session with ten mic inputs. The setting is user-visible so advanced users can tune it; the default is a size-balanced guess.

Freeze's tradeoff is conceptually similar to bus freezing in other DAWs: you lose the ability to edit upstream plugins without re-rendering. The engine's implementation is tidy because freeze is just a plugin (FreezePointPlugin) marking the cut — any plugin chain can be frozen, any sub-chain can be left live. The builder chooses at graph-build time.

Open questions

How does comp playback handle fades at the boundaries between sections from different takes? A naive implementation clicks; a careful one applies short cross-fades. The CompManager owns that metadata but the actual fade logic is graph-side, and likely inside FadeInOutNode or a helper used by CombiningNode. Worth a closer look for the glossary.

Notable omission: punch-in / punch-out UI details and the many-takes "loop record" mode aren't drawn here. Both are variants of the same recording path, with the loop-record mode accumulating successive takes as sibling clips that WaveCompManager can then consume.
