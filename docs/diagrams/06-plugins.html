06 · plugins & racks

Plugins & racks

One abstract Plugin base class, four concrete families that inherit it (internal effects, external hosts, ARA, and routing glue), a PluginManager that owns the registry, and a rack system that turns a sub-graph into a reusable plugin.

Concept: everything is a Plugin

The engine's plugin model is deliberately flat. One abstract base — Plugin, in tracktion_engine/plugins/tracktion_Plugin.h — defines the contract: initialise(), deinitialise(), applyToBuffer(), plus state ownership through juce::ValueTree. Everything a track can host inherits from it: built-in effects (EQ, compressor, delay), the FourOsc synth, the external plugin host wrapper, the ARA node, and — importantly — the routing-and-structure pieces (VolumeAndPan, LevelMeter, AuxSend, AuxReturn, RackInstance, InsertPlugin). There is no separate "routing object" hierarchy; routing is just a plugin whose applyToBuffer does something structural instead of something spectral.

PluginManager owns the registry. It wraps a juce::AudioPluginFormatManager and a KnownPluginList for scanning disk-installed plugins (VST3, AU, LV2, CLAP via JUCE formats), and it keeps a list of built-in types that the engine ships itself — every class in plugins/effects/ and plugins/internal/ registers a BuiltInType factory. A PluginCache lives on each Edit and hands out Plugin::Ptr instances (ref-counted) keyed by their EditItemID in the ValueTree.

Implementation: the four families

Internal effects (plugins/effects/) are the shipped DSP — Compressor, Chorus, Delay, Equaliser, LowPass, PitchShift, Phaser, Reverb, ToneGenerator, ImpulseResponsePlugin, LatencyPlugin, FourOscPlugin (synth), MidiModifier, MidiPatchBay, SamplerPlugin. Each one is a Plugin subclass whose applyToBuffer does its processing in-place on the buffer it's given.

Internal structural (plugins/internal/) are the plugins that exist to wire the graph, not transform samples: VolumeAndPan, LevelMeter, VCA, AuxSend/AuxReturn, RackInstance (a pointer to a shared rack), InsertPlugin (hardware insert round-trip), FreezePoint (marks where track-freeze cuts), ReWirePlugin, TextPlugin. The fact these are in the same hierarchy as an EQ is what lets them appear in the same plugin list UI and be serialised uniformly as ValueTree children of a track.

External hosts (plugins/external/) — principally ExternalPlugin — wrap a juce::AudioPluginInstance (the JUCE object for a hosted VST3/AU/CLAP/LV2). ExternalPlugin::applyToBuffer forwards the block to the wrapped instance and hosts its editor via PluginWindowState. The PluginManager::createPluginInstance callback is the customisation hook — a host app can override it to use its own sandboxed scanner or out-of-process plugin bridge.

ARA (plugins/ARA/) is a different kind of host. An ARA-aware plugin (Melodyne, SpectralLayers) sees the source audio at document scope, not per-block. The engine provides ARAFileReader, ARAPluginFactory, and a set of wrapper interfaces that let an ARA plugin consume the Edit's clips as an ARA document. The ARANode from diagram 4 is what sits in the audio graph; this diagram shows who it talks to.

Racks (plugins/internal/tracktion_RackType.h, tracktion_RackInstance.h) are a small but interesting piece. A RackType holds a sub-graph of other plugins — a reusable processing unit. A RackInstance is a plugin that embeds a reference to a RackType. Multiple tracks can point at the same RackType; changes propagate to every instance because they all share one ValueTree. At render time a RackInstance becomes the RackInstanceNode / RackNode / RackReturnNode trio from diagram 4.

Tradeoff: uniform hierarchy vs. semantic flattening

Making volume, pan, metering, and aux sends into "plugins" has obvious upsides: one serialisation path, one window manager, one automation-parameter pipeline, one list widget. The cost is ontological — a newcomer reading the code sees VolumeAndPanPlugin and has to mentally file it differently from ReverbPlugin, even though they're sibling classes. The engine picks uniformity and pays the conceptual cost. It's the right call given how much downstream machinery (automation from diagram 11, freezing from diagram 10) works on "a list of plugins."

The other tradeoff lives in PluginManager::createPluginInstance — being a std::function callback rather than a virtual method lets embedders inject sandboxed or out-of-process instantiation without subclassing, but it also means instantiation policy is not expressed in the type system, so finding out how a given host instantiates plugins means grepping for assignments to that function.

Open questions

The airwindows folder ships a copy of the Airwindows collection as part of the engine itself. That's a substantial third-party DSP inclusion sitting alongside plugins/effects/. It raises a question: are those exposed as built-in types on par with the native effects, or only if a compile-time flag (TRACKTION_AIR_WINDOWS) is set? The PluginManager::initialiseAirWindows() method is guarded by that flag — worth a closer read when writing the glossary.
