02 · how the pieces stack

Module dependency graph

The four Tracktion modules — tracktion_engine, tracktion_graph, tracktion_core — plus JUCE and the vendored 3rd-party tree underneath them. Built from the BEGIN_JUCE_MODULE_DECLARATION blocks and the actual #include lines at the top of each module's master header. Where they disagree is one of the more interesting flags on the site.

Concept: three Tracktion modules, in three layers

Tracktion Engine is shipped as three JUCE modules stacked on top of JUCE itself. tracktion_core holds foundation types — strongly typed time, tempo math, a multi-writer seqlock, an abstract audio reader — and knows nothing about DAWs. tracktion_graph is a generic real-time DAG processor: a Node abstract base, a handful of built-in node types (summing, latency, connected), a lock-free multi-threaded player, and a PlayHead. It, too, is DAW-agnostic. tracktion_engine is the DAW itself — Edit, Track, Clip, plugins, MIDI, audio files. That vertical split is the point: you can ship the graph without the engine, and you can reuse core in things that aren't real-time at all.

Implementation: declared deps vs. actual includes

Each module begins with a BEGIN_JUCE_MODULE_DECLARATION block listing its dependencies for the JUCE build system. Those declarations are the solid edges in the top half of the diagram: tracktion_core declares only juce_audio_formats; tracktion_graph declares only juce_audio_formats; tracktion_engine declares juce_audio_devices, juce_audio_utils, juce_dsp, juce_osc, juce_gui_extra, and tracktion_graph. That last one is the only Tracktion-to-Tracktion dep ever declared.

But the header includes tell a messier story. tracktion_graph.h does #include "../tracktion_core/tracktion_core.h" directly — an undeclared dependency that the JUCE build system never sees. tracktion_core itself reaches into ../../3rd_party/ for choc and crill headers. tracktion_engine.h similarly hard-codes paths like "../3rd_party/crill/spin_mutex.h" and "../tracktion_graph/utilities/tracktion_PerformanceMeasurement.h". In other words, the JUCE module format is a polite suggestion; the compiler cares about the #include lines, and those cut across module boundaries freely.

Tradeoff: the 3rd_party split, and what it costs

There are two 3rd_party/ trees. modules/3rd_party/ holds the shared toolkit: choc, crill, expected, rigtorp, rpmalloc, libsamplerate, magic_enum, nanorange, doctest. modules/tracktion_graph/3rd_party/ holds moodycamel's concurrent queue and farbot — realtime primitives used by the graph's node player and buffer pool. That split is deliberate: the graph module is self-contained enough to ship alone, so the primitives it depends on live inside it. The cost is duplication pressure: anyone adding a realtime primitive has to decide which tree it goes into, and the wrong choice creates a cross-tree #include immediately.
