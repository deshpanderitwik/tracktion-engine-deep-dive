03 · the centerpiece

The Edit — document object model

What an Edit owns, how deep the ownership tree runs, and why most of it is a juce::ValueTree. If you understand this diagram you understand the engine: every other subsystem is either reading from this tree, writing to it, or rebuilding itself when it changes.

Concept: the document

An Edit is a song. One instance represents one arrangement: its tracks and clips, its tempo map, its automation, its plugin racks, its scene launcher, its MIDI and audio routing. A host app can hold several Edit instances at once (the engine tracks them in an internal ActiveEdits registry) but from the user's point of view, one Edit is one document on disk.

The surprising bit is that the Edit is barely a class at all. Most of its fields aren't values — they're thin C++ objects that wrap a juce::ValueTree node. The actual data lives in a tree, the C++ objects are a typed view over that tree, and save/load is just serializing the tree to XML. Mutations go through undoManager so the tree is the undo scope too.

Implementation: Engine owns Edit, Edit owns everything else

The first row of the diagram tells the real ownership story. The Engine does not hold an Edit by value or by unique_ptr. The host (or whatever called loadEditFromFile) holds the Edit; the engine just keeps a pointer in its ActiveEdits struct so callbacks can find live Edits by ID. That's why the engine→edit edge is flagged. It looks like parent→child but it is not — the arrow on a real ownership diagram would go the other way.

Below the root row, the tree is dense and mostly orthodox: an Edit owns a TrackList, a SceneList, a TempoSequence, a PitchSequence, a MarkerManager, a RackTypeList, a master plugin list, a master volume/pan plugin, an AutomationRecordManager, a ParameterChangeHandler, a ParameterControlMappings, a TransportControl, an AbletonLink adapter, an ARADocumentHolder, a TrackCompManager, an EditInputDevices, a PluginCache, a GlobalMacros, and a LaunchQuantisation. Almost all of these are std::unique_ptr members declared in tracktion_Edit.h and constructed from slices of the Edit's state tree in the constructor.

The ValueTree trick

Two fields in the root row carry the weight of the whole design: state and inputDeviceState. Both are juce::ValueTree members. state is the Edit proper — tracks, clips, tempo, automation, everything the user would expect to save. inputDeviceState is a second tree, persisted alongside the first, holding per-input routing and arming that's conceptually part of the Edit but is kept separate because it references devices the host machine may or may not have. That split is flagged. It trips up people who assume there's one XML blob per Edit and then wonder where their record-arming went.

The "Persisted in state" flow overlay traces the dotted edges from the state tree to the subtrees it actually owns on disk. The "Rebuilt per session" flow traces the ownership edges from Edit to the transient members — the UndoManager, TransportControl, PluginCache, AbletonLink bridge, the ARA holder, the parameter change handler, the automation recorder. These are recreated every time the Edit is loaded; none of them are in the saved XML.

What's flagged

Three things about this diagram are worth slowing down on. First, the ValueTree duality: the Edit is a ValueTree wearing a C++ hat, and there are two trees, not one. Second, TrackList recurses — a Track can own a TrackList of sub-tracks, which owns tracks that own more tracklists, which is how folder and submix tracks work. That's the self-loop on the arrangement lane. Third, the engine's grip on the Edit is advisory, not ownership. Miss any of those three and you will write code that either leaks, double-frees, or tries to read a field that is only valid mid-session.

Open question: is inputDeviceState really a separate concept or a historical accident? It behaves like a second document fragment tied to machine-local identifiers. A later diagram on audio/MIDI I/O should revisit this.
