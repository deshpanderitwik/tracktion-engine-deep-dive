Automation, modifiers & macros

Every knob that can move is an AutomatableParameter. Four sources can move it: a curve on the timeline, a modifier (LFO / envelope / step), a macro parameter, or an external controller via MIDI-learn or the control-surface layer.

Concept: one parameter, many drivers

The central type is AutomatableParameter, a ref-counted object that wraps a single scalar value (volume, filter cutoff, plugin parameter) plus the machinery for reading/writing it automatically. Everything that can host parameters extends AutomatableEditItem — Plugin, Modifier, clip effects, track itself. Parameters are discoverable through an AutomatableParameterTree attached to each item.

Four things drive a parameter. Automation curves — AutomationCurve inside an AutomationCurveList — are timeline-aligned, breakpoint-based value streams. Modifiers are live-running value sources (LFO, envelope follower, step sequencer, random, breakpoint oscillator, MIDI tracker) that output samples each block. Macro parameters are user-created parameters that can themselves be mapped to any other parameter — one knob controlling many. External control arrives as MIDI (MIDI-learn) or from a control-surface handler; both resolve to assignments in ParameterControlMappings.

Implementation: sources, modes, and the recording path

Curves are the familiar one. An AutomationCurveList lives under an AutomatableEditItem; each curve targets one parameter. Values are read via AutomationIterator, which walks breakpoints in time order during process(). AutomationMode governs write behaviour during recording: Read, Touch, Latch, Write — same semantics as other DAWs. AutomationRecordManager captures parameter moves made by the user (or by external MIDI) while transport is recording, applying the chosen mode and folding new breakpoints into the curve on stop.

Modifiers are the interesting piece. A Modifier is an AutomatableEditItem too — its output value can itself be automated — and it sits in a track's ModifierList alongside plugins. At the graph level a modifier becomes a ModifierNode (diagram 4); upstream of that, its value drives parameter targets it's been assigned to. Every shipped modifier type (LFOModifier, EnvelopeFollowerModifier, StepModifier, RandomModifier, BreakpointOscillatorModifier, MIDITrackerModifier) implements the same interface — take time, emit value. ModifierTimer is the shared clock abstraction they all use.

Macros: a MacroParameter is itself an AutomatableParameter. A MacroParameterList on any MacroParameterElement (which Plugin already is — see diagram 6) exposes them. That means macros compose: a macro can be automated by a curve, modulated by a modifier, driven by MIDI-learn, and it in turn drives other parameters. The composition is unlimited in principle.

External control comes through two classes. MidiLearnState plus MidiAssignable capture "learn this knob, map it to that incoming CC"; ParameterControlMappings holds persistent assignments — control-surface IDs and MIDI CCs both resolve to the same assignment store. ParameterChangeHandler is the callback point where external changes arrive and fan out to the target parameters.

Tradeoff: uniform abstraction, many paths through it

Making every live value source — curve, modifier, macro, external — route through the same AutomatableParameter write path is what allows the UI to show automation lanes for modifier outputs, for macros, for everything. The downside is that the rules for which source wins at any given moment (AutomationMode, touch state, modifier assignment, active macro) are not trivially explained. Most of the time only one source is active; the rules exist for the corner cases. The code pays a readability cost to make the feature behave sensibly when users combine them.

The AutomationIterator design — walking breakpoints in block order rather than evaluating each block independently — is the right call for realtime: it lets the process() pull next values cheaply without searching the curve. It does mean seeks need a seek-path on the iterator (which exists) and that curves edited mid-playback need cache invalidation (also exists).

Open questions

How does modifier output value get into parameters when the target parameter is on a plugin whose ModifierNode is processed after the consumer in the DAG? The dependency ordering must be resolved at graph-build time (createNodeForEdit), but the exact policy for forward-only modulation isn't obvious from the headers.
